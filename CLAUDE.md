## 1. Product in one paragraph

A healthcare platform with two layers. The **EMR** is the clinical record: patients, vitals, diagnoses, consultations, prescriptions, lab and imaging. The **HMS/ERP** runs the facility: appointments and OPD queues, inpatient beds and wards, departments, billing and claims, inventory, staff and physicians, a patient portal, and accounting. One patient entry flows automatically into the chart, the invoice and the ledger. It is sold three ways: **SaaS** (multi-tenant, per doctor per month or tiered by active patients), **Enterprise licence** (same Docker image installed on the client's servers), and **custom deployment**. First market is assumed to be **Nigeria** (NDPA 2023 is the primary compliance frame; HIPAA and GDPR are design benchmarks). Target users: clinics and mid-size hospitals first.

### Module boundary rules (enforced by a pytest test)

- Each module is a Django app under `apps/` and owns its models, serializers, views, services, tasks and tests.
- A module may call another module **only through its `services.py` functions** (or publish a domain event). It never imports another module's models for writing and never queries another module's tables directly. A read-only foreign key to another module's model is allowed; business logic is not.
- Cross-module reactions use **domain events** (Django signals wrapped in `core.events`) whose handlers enqueue Celery tasks. The clinician's request never waits for billing or stock work.
- Enforce with one plain pytest test (`tests/test_module_boundaries.py`) that parses imports with the standard `ast` module and fails if a module imports another module's `models` for writing or anything other than `services`, `events` or `selectors`. No extra tool.

### Multi-tenancy

- Every tenant-owned row carries `tenant` (FK). A default manager filters by the current tenant; the current tenant is resolved from the authenticated user or host name and stored in a context variable.
- Tests must prove a user in tenant A cannot read or write tenant B (SEC-07). Schema-per-tenant is the fallback if a customer needs stricter isolation.
- Enterprise installs run the same code with a single tenant.

### Request pipeline (every request, in order)

1. HTTPS only → 2. authenticate (session or token, optional MFA) → 3. protect (rate limit, validation, CSRF, secure headers) → 4. authorise (role × attributes: facility, care team, purpose) → 5. business rules → 6. append to audit log → 7. data access (ORM, private storage). A denied request stops at step 4 and is still audited. UI visibility is never used for access control.

## 4. Modules and scope

**Release 1: clinical core.** accounts (roles, MFA, break-glass), tenants, patients (MRN, duplicates, allergies), clinical (vitals, diagnoses, consultation notes), scheduling (appointments, calendar, OPD queue, reminders), pharmacy (prescriptions, interaction and allergy checks, formulary), staff and physicians (licences, shifts, fees), basic billing, audit.

**Release 2: hospital operations.** inpatient (admissions, beds, wards, nursing and discharge plans), departments and units, diagnostics (lab tests and requests, imaging orders and reports), patient portal, HMO/insurer billing and claims, inventory and stock, dashboards.

**Release 3: specialty and ERP.** Pediatrics, surgical, e-prescribing, external lab and PACS integration, ERP apps (HR / employees, accounting and invoicing, inventory, internal messaging, website).

**Out of scope for now:** native mobile apps, payment-gateway settlement beyond recording status and reference, offline-first operation (decision pending, Section 12), a standalone FHIR server.

## 5. Domain rules that must be implemented exactly

### Patients
- **MRN**: generated by a background-safe, deterministic sequential generator from registration year plus a per-tenant sequence. Unique, never reused, never edited by users.
- **Duplicate detection**: before saving a new patient, score a *fuzzy* match on first name, last name, date of birth and national ID (national ID is optional). If the partial-match score is above 85%, do not create the record; flag it for manual duplicate review. Use fuzzy matching (for example trigram or Levenshtein), not hashing; hashes cannot give partial matches.
- **Status**: Active, Inactive, Deceased. Setting **Deceased** triggers an event that cancels active and recurring appointments, flags outstanding invoices for estate-settlement review, and revokes patient-portal access.
- **Names** allow letters, spaces, hyphens, apostrophes and accents. **IDs are foreign keys**, not alphabetic text.
- Allergies are a first-class structured field (substance, reaction, severity), used by the interaction check.
- Clinical records are **never hard-deleted by users**. "Entered-in-Error" hides a record from the active chart; history stays.

### Vitals
- Coded with LOINC; units in UCUM; BMI computed automatically from height and weight; each reading has a recorded timestamp, recorder and encounter/appointment link. (The source document's vitals table had copy-paste errors; the corrected model is in Appendix A of the PRD.)

### Diagnoses
- ICD-10 / SNOMED CT coded. **Clinical status**: Active, Recurrence, Remission, Resolved, Inactive. **Verification status**: Unconfirmed/Suspected, Confirmed, Refuted, Entered-in-Error. Resolved diagnoses require an abatement date. Diagnoses can be ranked per encounter.

### Appointments (one entity, defined once)
- Seven states: **Booked → Confirmed → Checked-In → In-Consultation → Completed**, plus **No-Show** and **Cancelled** (cancellation reason required).
- No double-booking of a physician slot; emergency type may overbook.
- On Booked: send SMS and email confirmation with an ICS calendar file. Reminders on a configurable schedule.
- On Checked-In: broadcast over WebSockets so the physician's queue updates live, sorted by arrival time and triage priority. Record the check-in clerk.

### Prescriptions and safety
- Authorising a prescription runs the drug-interaction and allergy check **before** signing. A blocking alert requires an override reason, which is logged.
- The signature is cryptographic and tamper-evident (SEC-09). After signing, raise `prescription.authorised`.
- Event chain (Celery): reserve stock → add invoice line item and recalculate net due → on dispensing, emit `dispensed` → billing line final → when the invoice is **Paid**, create the accounting entry (**Debit Cash/Bank, Credit Accounts Receivable**).
- Lab and imaging results finalised → saved to the chart and appended to the invoice.

### Inpatient and billing
- Admission with a bed assigned: bed state Vacant → Occupied in the **same database transaction**. A Celery beat job at **00:00** adds the daily ward charge to the pending ledger until discharge. Discharge status: Discharged, LAMA (left against medical advice), Transferred.
- Invoice payment status: Unpaid, Partially Paid, Paid. Insurer and patient split supported. Money is stored as integer minor units plus ISO currency code; never floats.

### Staff and physicians
- Licence numbers verified against the relevant medical council register; a **licence watcher** (Celery beat) flags expiring licences. Shift status: On-Duty, Off-Duty.

### Audit
- Append-only, tamper-evident log of every PHI read, create, update and delete: who, what, when, from where, and reason for break-glass. No update or delete path exists, in code or in the database role.

## 6. Security and compliance requirements (all mandatory)

| ID | Requirement |
| --- | --- |
| SEC-01 | HTTPS only (TLS 1.2+, 1.3 preferred); data encrypted at rest (database volume, object storage) |
| SEC-02 | Server-side RBAC + ABAC on every request |
| SEC-03 | Immutable audit log of all PHI access and changes |
| SEC-04 | Secrets in Railway variables per environment; never in Git, images or client bundles |
| SEC-05 | Private buckets; short-lived signed URLs; no public file URLs |
| SEC-06 | Rate limiting, input validation, secure headers, CSRF protection |
| SEC-07 | Tenant isolation in the data layer, proven by automated tests |
| SEC-08 | Automated PostgreSQL backups plus encrypted copy elsewhere; restore tested monthly |
| SEC-09 | Tamper-evident cryptographic prescription signatures |
| SEC-10 | Production access only for named engineers with 2FA; deploys only from the protected `main` branch after the local checks pass and a reviewer approves |
| DG-01..10 | NDPA 2023 frame: data minimisation, consent and lawful basis, data-subject rights, retention rules, residency decision for the Railway region, breach-response plan, DPIA before go-live, licence verification, legal evidential standing of e-records |

Performance targets (proposed): chart open under 2 s (p95), booking API under 500 ms (p95), 99.9% availability, 500+ concurrent users per tenant, recovery point 15 min, recovery time 4 h.

## 7. Roles (starting set)

Super admin (platform), Tenant admin, Doctor, Nurse, Pharmacist, Lab / imaging technician, Front desk / receptionist, Billing officer, Finance / accountant, HR, Compliance officer (audit review), Patient (portal). Permissions are role-based; attributes (facility, department, care-team membership, shift) narrow them. **Break-glass**: a clinician may open a chart outside their normal scope by giving a reason; it is logged and reviewed by the compliance role.

## 8. Quality bar and definition of done

- Every requirement implemented has tests; all tests pass; `make check` is green. It runs exactly two checks: `ruff` (lint plus format check) and `pytest`. The test suite includes the module-boundary test and a migration-drift test (`makemigrations --check --dry-run` must report no changes).
- Authorisation and tenant-isolation tests exist for every endpoint.
- Migrations are reversible where possible and never edited after merge.
- Clinical, pharmacy and billing logic is reviewed by a human with clinical or finance responsibility before release. AI review does not replace this.
- Acceptance criteria and a release is "done" only when: automations (MRN, duplicates, status cascade, licence watcher, ward charges, ledger sync) pass end-to-end tests; audit log verified complete and immutable; billing and ledger reconcile against test data; backups restored successfully once; no critical or high security findings open.

### Tooling choices

- Python 3.12, **uv** for dependency management, Django 5.x LTS-compatible stack, DRF, `drf-spectacular` (OpenAPI), `django-environ` or `environs`, `psycopg[binary]`, `celery`, `redis`, `channels`, `channels-redis`, `uvicorn` with `gunicorn`, `whitenoise`, `django-otp`, `django-storages[s3]`, `sentry-sdk`.
- Dev: `pytest`, `pytest-django`, `factory-boy`, `ruff` (lint and format). Nothing else: no mypy, import-linter, pip-audit or pre-commit framework.
- `make` targets: `install` (also runs `git config core.hooksPath .githooks`), `run`, `worker`, `beat`, `lint` (ruff check plus ruff format --check), `format`, `test` (pytest), `check` (**lint then test, only these two**), `seed`, `shell`, `up`, `down`.

### Railway setup (human does the clicks; Claude prepares the files)

1. Create one Railway project with two environments: `staging` and `production`.
2. Add services from the same GitHub repo: **web**, **worker**, **beat**, later **frontend**. Add the managed **PostgreSQL** and **Redis** plugins to each environment.
3. Start commands (all use the same Docker image):
   - web: `gunicorn config.asgi:application -k uvicorn.workers.UvicornWorker --bind 0.0.0.0:$PORT --workers 3`
   - worker: `celery -A config worker -l info --concurrency 4`
   - beat: `celery -A config beat -l info` (**exactly one replica**)
4. Web pre-deploy command: `python manage.py migrate --noinput`. Health check path: `/healthz` (returns 200 only if the database and Redis respond).
5. Variables per environment (never committed): `DJANGO_SETTINGS_MODULE=config.settings.production`, `SECRET_KEY`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `DATABASE_URL`, `REDIS_URL`, `S3_*` (endpoint, bucket, key, secret, region), `FIELD_ENCRYPTION_KEY`, `SENTRY_DSN`, SMS and email provider keys.
6. Deploy `staging` from `main` automatically on every push to `main` (the pre-push hook has already run the two checks locally). Deploy `production` by manual promotion or a protected tag.
7. Before any real patient data: confirm Railway region and terms against data-residency rules (DG-06), enable and test backups, set up an encrypted off-platform backup copy (SEC-08).

### GitHub setup (human)

Protect `main`: require pull request, one approval, a reviewer's approval, linear history; disallow force-push. Enable GitHub secret scanning (it is a setting, not a workflow). Add a CODEOWNERS file that requires the clinical lead or finance owner on `apps/pharmacy`, `apps/clinical` and `apps/billing`.

## 13. When to consider splitting the monolith

Only when at least one is true and measured: a module needs independent scaling that replicas cannot give; a separate team owns it and release coupling is slowing both; compliance requires isolation. Until then, keep one codebase and enforce boundaries with the boundary test so extraction stays cheap.
